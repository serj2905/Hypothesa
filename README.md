# Hypothesa — AI-интервьюер для проверки продуктовых гипотез

Hypothesa проводит короткие проблемные интервью вместо обычной формы с
галочками. Респондент отвечает своими словами, AI-интервьюер может задать одно
уточнение, а после завершения отдельный воркер превращает диалог в
структурированные наблюдения. Из накопленных ответов сервис выделяет темы и
использует их в следующих версиях анкеты.

## Как закрыты критерии задания

| Критерий | Что сделано |
|---|---|
| Доменная модель | `InterviewSession` — корень агрегата; внутри находятся вопросы, ответы, уточнения и события. Отдельно описаны завершённое интервью, тема, назначение темы и версия анкеты. Схема приведена ниже. |
| СУБД | PostgreSQL 16, SQLAlchemy 2 и пять последовательных миграций Alembic. Состояние диалога хранится в JSONB, аналитические сущности — в отдельных таблицах. |
| REST-интерфейс | FastAPI: создание и восстановление интервью, отправка ответов, удаление данных, healthcheck и автоматически сгенерированный OpenAPI. |
| Пользовательский интерфейс | Telegram-бот на aiogram: `/start`, согласие на обработку данных, последовательный диалог, уточняющие вопросы, сообщения об ошибках и `/delete_data`. |
| Тесты | Unit-тесты доменной логики, REST API, LLM-клиента, суммаризации, приватности и тематического цикла; интеграционный тест PostgreSQL проверяет optimistic locking и идемпотентность. |
| Docker | Один `Dockerfile` для API, бота и воркеров; `compose.yaml` поднимает PostgreSQL, Ollama, миграции, Telegram-бота, API и worker. |
| Масштабирование воркеров | Завершённые интервью разбирают независимые model workers. Задачи атомарно забираются из PostgreSQL через `FOR UPDATE SKIP LOCKED`, поэтому количество контейнеров меняется командой `--scale worker=N`. |

## Быстрый запуск в Docker

Понадобятся Docker Desktop / Docker Engine с Compose и NVIDIA Container
Toolkit. В `compose.yaml` Ollama использует GPU; первый запуск будет дольше
обычного, потому что нужно скачать две модели.

Скопируйте настройки:

```powershell
Copy-Item .env.example .env
```

В созданном `.env` заполните:

- `TELEGRAM_TOKEN` — токен бота, полученный у `@BotFather`;
- `PARTICIPANT_SALT` — случайная строка длиной не меньше 16 символов.

Запустите весь MVP:

```powershell
docker compose up --build
```

Когда в логах появится сообщение о запуске polling, откройте своего бота в
Telegram и отправьте `/start`. REST API будет доступен на
[http://localhost:8000/api/docs](http://localhost:8000/api/docs).

Остановить сервис:

```powershell
docker compose down
```

Данные PostgreSQL и модели Ollama останутся в Docker volumes. Команда
`docker compose down -v` удалит и данные, и скачанные модели.

## Telegram-интерфейс

Бот работает только в личных чатах. `/start` создаёт новую сессию и предлагает
дать согласие. Дальше все текстовые сообщения считаются ответами на текущий
вопрос. Сообщения одного пользователя сериализуются локом, а номер ревизии в БД
защищает сессию от одновременного обновления разными процессами.

Команда `/delete_data` удаляет активные сессии и завершённые индивидуальные
ответы участника. Telegram user id перед записью преобразуется в HMAC-псевдоним
и в исходном виде в PostgreSQL не попадает.

## Масштабирование model workers

Один воркер поднимается вместе с обычным `docker compose up`. Например, чтобы
обрабатывать очередь тремя экземплярами:

```powershell
docker compose up -d --scale worker=3
docker compose ps
```

Очередь здесь реализована без отдельного брокера:

1. завершённая сессия получает статус `pending_summary`;
2. воркер одной транзакцией выбирает свободные строки с блокировкой
   `FOR UPDATE SKIP LOCKED`;
3. генератор строит структурированную сводку;
4. модель другого семейства проверяет её на галлюцинации;
5. результат идемпотентно записывается в `completed_interviews`.

Если воркер упал, зависшая задача через 30 минут снова становится доступной.
После трёх неудачных попыток она получает статус `summary_failed`, а текст
ошибки остаётся в БД для диагностики.

На одном компьютере с одной полностью загруженной GPU несколько воркеров не
обязательно дадут прирост. Такой способ масштабирования полезен, когда воркеры
запускаются на нескольких машинах и подключены к общей PostgreSQL и доступным
им model endpoints. Это сознательное ограничение, а не обещание ускорения от
одного только увеличения числа процессов.

## Архитектура

Telegram и REST API — два тонких входных адаптера. Они ничего не знают о
промптах, структуре хранения и тематическом анализе, а вызывают одни и те же
функции `start_interview()` и `advance()`. Поэтому правила интервью тестируются
один раз и одинаково работают через оба входа. Состояние хранится в PostgreSQL,
live-запросы к модели выполняются через Ollama, завершённые интервью разбирают
фоновые workers, а scheduler обновляет темы и адаптивную анкету.

## Доменная модель

`InterviewSession` хранится как агрегат в JSONB. Это позволяет атомарно
сохранять текущий вопрос, первоначальный ответ, уточнение и номер ревизии, не
собирая живой диалог из множества строк. При этом события, финальные результаты,
темы и версии анкет вынесены в отдельные таблицы, потому что по ним нужны
выборки и аналитика.

Основные сущности: участник с псевдонимным идентификатором, сессия интервью,
событие диалога, завершённое интервью, тема, назначение темы на ответ, версия
анкеты и запуск тематического анализа.

Важные инварианты:

- у участника может быть только одно активное интервью одного исследования;
- любое обновление проверяет номер `revision` и не допускает lost update;
- отказ до согласия удаляет созданную pre-consent сессию;
- одинаковое событие и итоговая сводка не записываются дважды;
- внешний UUID REST-клиента и Telegram user id не хранятся напрямую — в БД
  попадает только HMAC-псевдоним.

## REST API

| Метод | URL | Назначение |
|---|---|---|
| `GET` | `/health` | Проверить API и соединение с PostgreSQL |
| `POST` | `/api/v1/interviews` | Создать новое интервью |
| `GET` | `/api/v1/interviews/{id}` | Получить состояние и текущий вопрос интервью |
| `POST` | `/api/v1/interviews/{id}/messages` | Передать ответ в доменную логику и модель |
| `DELETE` | `/api/v1/participants/me` | Удалить все данные текущего респондента |

Пример создания интервью:

```bash
curl -X POST http://localhost:8000/api/v1/interviews \
  -H "Content-Type: application/json" \
  -d '{"participant_token":"2fae6df5-869c-49c8-b432-1abcc0f34937"}'
```

REST-клиент создаёт случайный UUID участника. Перед записью он псевдонимизируется
с помощью `PARTICIPANT_SALT`. Чужое интервью нельзя получить только по его
`interview_id`: сервер также проверяет владельца.

## Тесты

Установить зависимости и запустить быстрый набор:

```powershell
python -m pip install -r requirements.txt
python -m pytest -q
python -m ruff check .
python -m ruff format --check .
```

Без `TEST_DATABASE_URL` пропускается только PostgreSQL integration test.
Полный прогон:

```powershell
docker compose up -d postgres
$env:TEST_DATABASE_URL = "postgresql+psycopg://postgres:postgres@localhost:5432/hypothesa"
python -m pytest -q
```

Тестируется именно критическая логика, а не учебные арифметические функции:
переходы интервью, согласие и отказ, единственное уточнение, structured output
LLM, retry, псевдонимизация, удаление PII, REST-входы, конкурентное обновление
сессии, идемпотентная суммаризация и тематический цикл.

## Оценка BERTopic

Быстрая проверка BERTopic на размеченном аспектном smoke-корпусе:

```powershell
python -m eval.run_topic_eval --quick
```

Полная сетка параметров UMAP/HDBSCAN для MiniLM и multilingual E5:

```powershell
python -m eval.run_topic_eval
```

Отчёт сохраняется в `eval/results/` и сравнивает долю шума, silhouette,
Adjusted Rand Index и чистоту назначенных кластеров. Разметка smoke-корпуса
проверяет аспекты обслуживания; она не заменяет ручную оценку тем на реальных
интервью.

Read-only preview на текущем faithful-корпусе PostgreSQL:

```powershell
python -m eval.preview_topics
```

Команда печатает темы, вероятности и репрезентативные примеры, сохраняет JSON в
`eval/results/`, но не обновляет таблицы тем, назначения или адаптивную анкету.

Рядом с каждой темой выводится распространённость — доля интервью с упоминанием,
а не доля документов, — с 95% доверительным интервалом Уилсона:

```text
Темы: 2; шум: 10 (45.5%); покрытие топ-5: 54.5%; silhouette: 0.081

[0] комиссия, перевод, лимит (7 документов; 7 из 22 интервью — 32%, 95% ДИ 16%–53%)
[1] очередь, отделение (5 документов; 5 из 22 интервью — 23%, 95% ДИ 10%–43%)
```

Интервалы намеренно показаны рядом: на пилотных выборках они шире расстояния
между соседними темами, поэтому рейтинг читается как подсказка порядка, а не как
измерение распространённости. Тот же интервал возвращает `calculate_ratings` в
поле `prevalence_ci95` для тем реального цикла.

Для локального end-to-end теста можно идемпотентно создать отдельный synthetic
survey с 50 grounded faithful-интервью:

```powershell
python -m eval.seed_faithful_interviews --apply
python -m eval.preview_topics --survey-id sber-service-quality-synthetic-v1
```

Seed не вызывает LLM и не смешивается с основным survey: raw-ответы и summary
строятся вместе, а summary-items проверяются на присутствие в исходном ответе.

## Основные настройки

| Переменная | Значение по умолчанию | Для чего нужна |
|---|---|---|
| `DATABASE_URL` | PostgreSQL `hypothesa` | Подключение к хранилищу |
| `OLLAMA_HOST` | `http://localhost:11434` | Адрес model endpoint |
| `LLM_MODEL` | `qwen2.5:14b-instruct-q4_K_M` | Интервьюер и генератор сводки |
| `JUDGE_MODEL` | `llama3.1:8b` | Независимая проверка сводки |
| `TELEGRAM_TOKEN` | нужно заполнить | Токен основного интерфейса респондента |
| `PARTICIPANT_SALT` | нужно заменить | HMAC-псевдонимизация участников |
| `API_MAX_CONCURRENT_LLM_REQUESTS` | `2` | Лимит одновременных REST-запросов к модели |
| `WORKER_BATCH_LIMIT` | `10` | Сколько сессий забирает один воркер |
| `WORKER_POLL_SECONDS` | `5` | Пауза между проверками очереди |
| `DATA_RETENTION_DAYS` | `90` | Срок хранения индивидуальных данных |

Полный список с пояснениями находится в [.env.example](.env.example).

Все зависимости проекта собраны в одном `requirements.txt`: runtime, BERTopic,
эмбеддинги, тесты и статический анализ.

```text
│   ├── storage.py          # таблицы и PostgreSQL repository

│   ├── topics.py           # тематическое моделирование
│   ├── automation.py       # условия offline-пересчёта
│   └── privacy.py          # редактирование PII
├── eval/                   # golden-eval и оценка тематического моделирования

├── tests/                  # unit и integration tests
├── bot.py                  # основной интерфейс респондента
├── Dockerfile
├── pyproject.toml           # настройки Pytest и Ruff
└── compose.yaml
```
